### 1.2 Exact recommended launch flags on 64 GB (single seat + resident router)

Flag semantics are from the auto-generated `llama-server` help table in
https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md (fetched
2026-11-14; defaults quoted from that table). The registry argv is kept; the additions are
the smallest set that pins behaviour the eval claims:

- `-ngl 99` — all layers on Metal (already in argv).
- `-c {ctx}` — per-seat window (2048 router, 16384 hunt, 32768 daily/coding).
- `-fa on` — pin Flash Attention. Default is `auto`; the flag takes `on|off|auto`, and the
  function-calling doc's own examples run `--jinja -fa` (docs/function-calling.md, fetched
  2026-11-14).
- `-np 1` — one slot, so `-c` is the request's window instead of being split across slots
  (`-np` = number of server slots, default auto). The existing registry draft rows already
  pin `-np 1` for spec cells; extending it to plain makes plain and spec comparable.
- `--jinja` (already in argv) — template-driven chat, tools, and reasoning parsing. Note
  `--jinja` is now the server default (`--jinja, --no-jinja … default: enabled`), the argv
  pin stays harmless.
- `--reasoning-format auto` (default) or `deepseek` — none | deepseek | deepseek-legacy;
  `auto` detects from template. `-rea, --reasoning on|off|auto` (default auto) is the
  think on/off switch, and `--reasoning-effort` / `--reasoning-budget` exist for the Qwen
  3.8 seat's per-request effort control. All four flags are in the help table above.
- `--cache-reuse 256` — min chunk size for KV-shift prompt-cache reuse (default 0); the
  prompt cache itself is on by default with `--cache-ram 8192` MiB cap (help table). This
  is the prefix-cache lever for the router's repeated intent prompt.
- `--moe-cache-mib 0` (default, disabled) is correct on 64 GB today: Nemotron Q4_K_M is
  25.48 GB and Gemma QAT q4_0 is ~15 GB class, both fit whole-GPU without expert spilling,
  so the new host-memory MoE expert cache (`--moe-cache-mib`, `--moe-cache-cpu-share`,
  v1.0.0 release notes) should stay off until co-residence pressure says otherwise.
- Speculative decoding: `--spec-type draft-mtp --spec-draft-n-max 3` — `draft-mtp` is in
  the upstream `--spec-type` list (none, draft-simple, draft-eagle3, **draft-mtp**,
  draft-dflash, draft-dspark, draft-dflash2, draft-lilicorr, ngram-*) with
  `--spec-draft-n-max` default 3 (help table). bartowski's Nemotron README gives exactly
  `--spec-type draft-mtp` for these quants. Draft-model cells use
  `-md {draft_gguf_path} -ngld 99` (flags in the same table). Streaming: the server lists
  "Speculative decoding" as a server feature and `GET /slots` reports a per-slot
  `speculative` boolean (server README, fetched 2026-11-14) — but whether streamed tokens
  behave identically under `draft-mtp` is a **preflight question for the orchestrator's
  canary**, not something this lane verified.
- Memory limit: on unified memory llama.cpp can use ~75% of RAM for the GPU by default;
  ggerganov in discussion #4167 points at discussion #2182 for raising the wired limit
  (fetched 2026-11-14). The repo's swap guard (guard block, engine_h2h.yaml: growth 2048 MB,
  start-used 4096 MB) is the practical cap; `--fit` (default on) adjusts unset arguments to
  fit device memory, `--fit-target` default 1024 MiB margin (help table). `-lm mmap`
  (default `auto`) keeps load pageable, which is what you want beside a live stack.
- Metal specifics: ggml v1.0.0 brings "few-row quantized matmuls and MoE fusion on
  CUDA/Metal" (v1.0.0 release notes). `--swa-full` exists for full-size SWA caches (Gemma
  families use sliding-window attention; help table links PR #13194) — leave default
  (false), which is the memory-lean behaviour.

### 1.3 Known version-specific bugs / limits for these families

- **Gemma 4 tool-call-inside-thought parsing**: open PR #32232 (2026-11-13, "merge ready")
  fixes issue #32231 — "The thought channel is normally closed with <channel|>, but the
  model may open it and go straight to a tool call without closing it", which swallows the
  following tool call (https://github.com/ggml-org/llama.cpp/pull/32232, fetched
  2026-11-14). Directly relevant to hunt/council tool probes on a build without the fix;
  pin or verify the build contains it.
- **Qwen3+/Gemma4 token-aware parsing cost**: open PR #29307 documents that chat parsing
  runs on text, so `<think>` emitted as pieces mis-parses, and trigger-pattern matching via
  `std::regex` costs Gemma 4 949 µs and Qwen3.8 1,014 µs per token at 64k context with
  tools offered (PR grammar path: 1.2/1.1 µs) — an open, measurable decode tax on exactly
  our two tool seats (https://github.com/ggml-org/llama.cpp/pull/29307, fetched 2026-11-14).
- **MTP on the wrong shape of problem is a slowdown**: PR #27788's annex measured
  Qwen3.5-4B-MTP at **0.47× (−53%)** on a fast GPU, gemma-4-12b split-weight MTP-4 at
  **1.18×**, draft budget 5–6 as the sweet spot, and states any speculative mode with
  model layers on CPU is a slowdown (https://github.com/ggml-org/llama.cpp/pull/27788,
  fetched 2026-11-14). Our seats are 27–30 B and fully Metal-resident, the favourable case,
  but the acceptance-rate gate is the run's own preflight.
- **Gemma 4 MTP is split-weight**: Gemma 4 keeps its prediction heads in a separate
  "assistant" GGUF, not inside the target file (PR #27788 annex; ggml-org repo file list).
  A Gemma spec cell therefore needs `-md` with that draft file — not `draft-mtp` alone.
- **Quantized KV vs tool calling**: the function-calling doc warns "Beware of extreme KV
  quantizations (e.g. -ctk q4_0), they can substantially degrade the model's tool calling
  performance" (docs/function-calling.md, fetched 2026-11-14). Keep KV f16 for the tool
  seats; `-ctk/-ctv` now also accept `f8_e4m3` (v1.0.0 release notes).
- Fable-of-record from the landscape lane (docs/ENGINE_LANDSCAPE_20261111.md, 2026-11-11):
  Splash's own README benchmarked llama.cpp GGUF 27B at 16 tok/s vs Splash 74 on M5-class
  silicon — llama.cpp plain GGUF is not expected to be the speed story; MTP is.

### 1.4 How it reports tokens and resident memory (readback contract)

All from the server README (fetched 2026-11-14):

- Tokens: OpenAI-compatible `usage` (`prompt_tokens`, `completion_tokens`,
  `total_tokens`) in `/v1/chat/completions`; `/completion` returns a `timings` object
  (`prompt_eval_count`-style counts and `predicted_per_second`). `GET /metrics` (opt-in
  `--metrics`) exports Prometheus counters/gauges including `llamacpp:prompt_tokens_total`
  and `llamacpp:prompt_tokens_seconds`.
- Settings readback: `GET /props` (server + model state; the README notes the model *path*
  is there while the API alias is separate), `GET /slots?` per-slot state including
  `speculative: true/false`, `n_ctx`, sampler params — this is the endpoint that proves a
  spec cell actually turned spec on.
- Resident memory: `GET /models` exposes a `memory` field per model with
  `min/max/effective` measurements in bytes split per device into `model`, `context`,
  `compute` (router-mode doc section; on a single-model server the same measurement
  machinery exists via `--models-*`/fit; treat the field's presence on this exact build as
  **unverified until the canary reads it**). Second independent reading stays the
  harness's process-tree RSS / `vm_stat` wired delta (instrument contract).
- Load-time log lines (`KV buffer size`, `compute buffer size`, `offloaded X/Y layers`) are
  the classic static breakdown (seen verbatim in the Ollama-run llama-server log in ollama
  issue #19701, fetched 2026-11-14).

### 2.1–2.5 Per-seat summary

### 3.2 Flags on 64 GB (env + API, from docs fetched 2026-11-14)

All from https://raw.githubusercontent.com/ollama/ollama/main/docs/faq.mdx and
…/docs/context-length.mdx (both fetched 2026-11-14):

- Context: default **4096**; `OLLAMA_CONTEXT_LENGTH` sets the server default; VRAM-scaled
  defaults are **4k < 24 GiB, 32k at 24–48 GiB, 256k at ≥ 48 GiB** — on this 64 GB host the
  default is 256k, which is why the tags on disk carry baked `num_ctx` (ctx32k/ctx16k/ctx2k)
  and why the matrix treats the tag's baked context as the engine-reported value.
  Per-request `num_ctx` exists on `/api/generate`-style options; the repo's own finding
  stands that `/v1` ignores runtime `num_ctx` (instrument, engine_eval_instrument.py).
- Flash attention: **automatic when the backend supports it**; `OLLAMA_FLASH_ATTENTION=1/0`
  forces. KV cache type: `OLLAMA_KV_CACHE_TYPE` — `f16` default, `q8_0` "recommended if not
  using f16", `q4_0` noted as more lossy; **global for all models** and quantized KV needs
  flash attention.
- Concurrency: `OLLAMA_NUM_PARALLEL` default **1** and "required RAM scales by
  OLLAMA_NUM_PARALLEL × OLLAMA_CONTEXT_LENGTH"; `OLLAMA_MAX_LOADED_MODELS` default 3×GPU;
  `OLLAMA_MAX_QUEUE` 512. Keep-alive: 5 min default, `OLLAMA_KEEP_ALIVE` / per-request
  `keep_alive` (`0` unloads immediately — what Stage 0 uses).
- What the server actually runs: a 0.40.16 user log (issue #19701, fetched 2026-11-14)
  shows Ollama spawning llama-server with `-c … -np 1 … --flash-attn auto -b 512 -ub 512
  --context-shift --keep 4` and `spec common_specu: no implementations specified for
  speculative decoding` — **no speculative decoding is configured in 0.40.16**. That
  matches the landscape lane's note that 0.40.16 release notes don't mention MTP
  (docs/ENGINE_LANDSCAPE_20261111.md). Web search was unavailable in this lane (two
  cancelled queries), so "no Ollama spec knob exists at all" stays unproven; what is
  proven is that the flag set above is what 0.40.16 launches with.
- Tools/think: the production seats already drive tools and `think` through the Pipeline
  (think true on daily/coding, false on router — docs/ENGINE_EVAL_MATRIX_20261113.md), and
  `/api/show` exposes `parameters` including `think` (instrument). The tool-calling doc
  page on docs.ollama.com was **not** re-fetched in this lane (landscape said the same on
  2026-11-11) — carries as unverified here.
- Privacy nicety: `OLLAMA_NO_CLOUD=1` or `disable_ollama_cloud` in `~/.ollama/server.json`
  (faq.mdx) — the platform's zero-cloud value, and the log in #19701 shows it active.

### 3.3 Known version-specific bugs / limits

- No speculative path in 0.40.16 (log evidence above) → its GGUF rows can never carry the
  MTP lever that llama-server can.
- Repo-recorded: two models in flight deadlocked Ollama on 2026-09-21
  (docs/MIMO_V26_DISTILL_9B_BRINGUP_V1.md, via the landscape doc) — the harness lock exists
  for this; the router-beside-seat question is exactly this risk.
- Repo-recorded: Ollama 0.40 has no `/api/tokenize`; token counts use same-base tokenizer
  vs engine usage (tests/benchmarks/engine_eval_instrument.py header).
- Repo-recorded: `-ctxNk` tags are derived builds sharing the base weights blob; never
  repoint a seat to a smaller-context tag (WORKER_CONTRACT §10).
- From the docs themselves: KV cache type is global (one setting for every model on the
  server) — a q8_0 KV arm on the router would silently apply to a concurrently loaded
  seat; another reason cells run one engine at a time.

### 3.4 Token and memory reporting

- Tokens: OpenAI `/v1` `usage`, native `/api/chat`/`/api/generate` report
  `prompt_eval_count` / `eval_count` (instrument's same-base tokenizer cross-check).
- Memory: `GET /api/ps` rows give `size` and `size_vram` per loaded model, plus
  `context_length` and `expires_at` (instrument `parse_ollama_ps`; the Stage-0 baseline
  validated exactly this readback live on 2026-11-13 — docs/ENGINE_EVAL_MATRIX header and
  instrument docstring). CLI `ollama ps` prints SIZE / PROCESSOR / CONTEXT columns
  (faq.mdx, context-length.mdx). RSS is read separately and never added to `size_vram`
  (instrument memory rule).

### 3.5 Published M-series numbers

- This host (repo records): Nemotron GGUF Q4_K_M 52.9–53.1 t/s vs oMLX oQ4e-MTP
  70.0–70.3 t/s; Qwen3.8-27B GGUF 12.25–12.7 t/s (config/backends.yaml comments 2026-08-14
  and MLX_SERVE bench, via the landscape doc).
- Vendor-side: none found for 0.40.x on Apple Silicon in this lane (the release notes carry
  a memory claim, not a speed claim). The Rapid-MLX README's "Ollama on Mac has an MLX
  engine" sentence remains an unverified vendor sentence (landscape doc) — the v0.40.16
  asset list (darwin tgz has no MLX suffix) does not support it.

### 3.6 Operability

The most turnkey of the three: resident daemon, pull-based tags, keep-alive lifecycle,
`ollama ps` for everything the harness reads back. Cost: no spec lever, global KV setting,
one-model-at-a-time loading behaviour, and baked context in tags. It is already the
production failover path, which is precisely why the matrix says its rows do not decide
the MLX engine.

## 5. Which seats each GGUF engine can plausibly beat oMLX on

Incumbent pairs, on this host, from repo records (landscape doc compilation):
daily-moe = oMLX `NVIDIA-…-oQ4e-mtp` **70.0–70.3 t/s** vs Ollama GGUF Q4_K_M **52.9–53.1**;
coding = oMLX `Qwen3.8-27B-oQ4e-mtp` (production path via alias) with DFlash2 drafter on
disk, oMLX plain-4bit ~15 t/s vs Ollama GGUF 12.4–12.7; hunt/council = oMLX
`gemma-4-26b-a4b-it-QAT-4bit` (no published oMLX t/s row found in the repo docs this lane
read); router = GGUF-only by definition.

| Seat | brew-llama | prismml-llama | Ollama | Reasoning |
|---|---|---|---|---|
| daily-moe (Nemotron 30B-A3B) | **Best GGUF shot, and the only same-bytes spec pair**: Q4_K_M already 53 t/s on Ollama; `draft-mtp` is vendor-documented for exactly this quant; A3B MoE is bandwidth-friendly and ggml 1.0.0 added Metal MoE fusion. To *beat* oMLX's 70 t/s it must clear +33% over Ollama — plausible arithmetic (273 GB/s ÷ ~17 GB/token active @4.5 bpw ≈ 160 t/s ceiling) but **unproven**; MTP acceptance on a chat workload is the risk | Same story minus version currency; the differentiators (async uploads, GDN) don't target nemotron_h | Loses today at 53 vs 70; no spec lever | Different bytes than the oQ4e-mtp sidecar either way — a "win" moves the *GGUF failover tag*, not the oMLX seat, per the matrix |
| coding (Qwen3.8-27B dense GDN-hybrid) | Plain GGUF Q4_K_M ~25 GB: ~12.5 t/s incumbent-class, no headroom story; with the unsloth MTP GGUF as `-md` draft it is the one candidate that could jump — but the draft is not on disk, and MTP helps only fully-resident, bandwidth-bound ≥8B models (PR #27788) — this seat qualifies on size, unproven on Metal | **The fork's real target**: its qwen35 GDN single-sequence fused decode is aimed at exactly this family — worth one cell against brew as control | 12.4–12.7 t/s incumbent; production coding path is oMLX-aliased; no win path without spec | Unlikely to beat oMLX oQ4e-mtp+DFlash2. GGUF upside is speculative-only |
| hunt/council (Gemma 26B-A4B QAT) | QAT-q4_0 GGUF is the artifact; A4B MoE + Metal MoE fusion gives the same ceiling argument as daily-moe, but no on-disk drafter (matrix: do not download) and the gemma4 tool-call parse bug (#32232) sits on the tool path | Same, plus version-skew risk on the gemma4 parser | Serves the QAT tag today; speed unrecorded in repo docs | Most likely to stay oMLX: the QAT quality artifact is identical family and oMLX's MLX QAT-4bit is the seated incumbent; a GGUF win would be a pure-speed result, none found published |
| task-router (E4B GGUF 2k) | **Strongest co-residence candidate**: 5.3 GB weights, 2k ctx → KV is negligible under `--cache-reuse`; llama-server is one process the harness starts/stops per cell, unlike the resident Ollama daemon sharing the global KV setting. Speed at 128-token predicts is TTFT-dominated and nobody publishes it | Same, whichever builds faster; both are interchangeable here on contract | Current production path; fine, but global KV type + cross-model overlap deadlock history are exactly the router-beside-seat risks the matrix calls out | "Beats oMLX" is undefined here — no MLX checkpoint is named for the router (matrix). The real question the matrix asks: can it hold the router beside the seat without tripping the swap gate. 5.3 GB + tiny KV says yes on paper; co-residence is the live test |

Bottom line for the operator's stated expectation: nothing in the GGUF research contradicts
"MLX variants (vLLM-MLX family) beat production". The one GGUF lever that could surprise is
llama-server `draft-mtp` on the Nemotron Q4_K_M — vendor-documented, same-bytes-compatible,
and aimed at the bandwidth-bound case — and the one fork-specific lever is PrismML's GDN
decode path on Qwen3.8. Both are bench questions, not claims.
