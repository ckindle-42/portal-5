# vLLM on Apple Silicon: pre-run research (2026-11-14)

## Scope and conclusion

This is a source review for the pinned `vllm-mlx==0.6.0` and `vllm-metal==0.33.0` releases on a 64 GB Apple Silicon host. It is not a model-load, API, or speed result. No engines were started, and no weights were downloaded. Vendor and community sources below were reviewed 2026-11-14; release dates are stated where the source is a versioned release.

The strongest evidence for an oMLX win is **vllm-metal at concurrent Qwen3.8 serving**: the vendor published M5 Pro 64 GB comparisons on Qwen3.8 itself and says vllm-metal has the lowest TTFT and end-to-end latency at concurrency 2 and 4, while oMLX leads at concurrency 1. A community recipe reports 16.4, 47.1, and 52.85 output tokens/s at concurrency 1, 4, and 8 on an M5 Pro 64 GB using the same 4-bit Qwen3.8 family. Those are self-reported results, not an oMLX comparison. The current local H2H record says this exact Qwen artifact failed to load with `Unrecognized image processor`, so that seat is not eligible until the existing on-disk copy passes a fresh load preflight. vllm-metal is also the strongest concurrent-serving candidate for the Gemma QAT seat, but there is no published result for the exact 26B QAT target and its Gemma tool parser has open upstream issues.

**vllm-mlx has the best specific speculative-decoding candidate for daily-moe** because the local oQ4e model includes its native Lightning MTP head and the v0.6.0 CLI supports native MTP. That is a candidate, not a proven speed win. vllm-metal marks Nemotron-H experimental, disables its prefix cache, and rejects MTP/draft-model speculation for its Mamba2 hybrid state family. Neither engine can serve the task-router artifact as configured: it is a Gemma 4 E4B MoE GGUF, while vllm-mlx expects MLX checkpoints and vllm-metal's v0.33 GGUF support excludes MoE. No EAGLE head or EAGLE method is documented for either pinned Apple backend; vllm-mlx SpecPrefill is prompt-prefill acceleration, not decode speculation. ([vllm-mlx v0.6.0 CLI](https://github.com/waybarrios/vllm-mlx/blob/v0.6.0/vllm_mlx/cli.py), [vllm-metal v0.33.0 speculation guide](https://github.com/vllm-project/vllm-metal/blob/v0.33.0/docs/speculative_decoding.md), reviewed 2026-11-14.)

## Local inventory and mismatches

The H2H model and engine records were read from [`tests/benchmarks/engine_h2h.yaml`](../../tests/benchmarks/engine_h2h.yaml) and [`config/bench_engines.yaml`](../../config/bench_engines.yaml) on 2026-11-14. The task rows specify contexts 32,768 for Nemotron and Qwen3.8, 16,384 for Gemma QAT, and 2,048 for the task-router GGUF; they specify a 6,000-token prefill workload for the MLX model rows. The current Qwen tool parser is `hermes`; Gemma is `auto`; Nemotron is `auto`.

There is a seat-definition mismatch: the requested scope groups hunt and council under Gemma 4 26B A4B QAT, but the current H2H mapping assigns `hunt` to `gemma4_26b_a4b_qat` and `council-json` to `qwen38_27b_h2h`. Therefore, the council recommendation below is a proposed Gemma seat recommendation; it does not describe what the current `council-json` H2H row loads.

The installed registry argv currently pins vllm-mlx 0.6.0 and uses continuous batching, but it applies `enable_thinking:false` to every seat. That conflicts with Qwen3.8's default thinking-on behavior and the requested hunt reasoning workload. The registry's Metal command uses `--gpu-memory-utilization 0.45 --max-model-len {ctx}` and `--trust-remote-code`; it has no cache or parser arguments yet. The H2H file already records `vllm-metal` as excluded for Qwen3.8 because of the image processor error. These are local file facts, not claims re-probed against a running service.

### Shared 64 GB argv and cache behavior

For the three MLX checkpoint seats, use this baseline launch template and fill `{model}`, `{served}`, `{port}`, `{ctx}`, and the seat parser. The local Metal config reports that 0.45 was chosen on the 64 GB host on 2026-11-13; this is only a conservative vllm-mlx starting point, not a vllm-mlx tuning result. In v0.6.0, `--gpu-memory-utilization` sets the fraction for the Metal allocation limit and emergency cache-clear threshold; it does not cap whole-machine memory or guarantee against OOM. `--max-kv-size` is the per-sequence RotatingKVCache limit and can evict early context; keep Qwen at 32,768 to preserve long reasoning. `--max-request-tokens 8192 --max-tokens 8192` makes 8,192 a hard generation-request ceiling (the former registry template set the request ceiling to the full context, so its 8,192 default was not a hard cap). Prefix caching is enabled by default; `--cache-memory-mb 2048` caps its memory-aware cache budget. `--continuous-batching` enables concurrent scheduling, and `--max-num-seqs 4` bounds live sequences. Leave the `--prefill-batch-size`/`--completion-batch-size` defaults (8/32) behind that four-sequence cap until measured; `--prefill-step-size 512` chunks long prompt prefill. Leave `--use-paged-cache` off initially because the guide presents it as a separate optional cache path. ([v0.6.0 CLI source](https://github.com/waybarrios/vllm-mlx/blob/v0.6.0/vllm_mlx/cli.py), [CLI reference](https://github.com/waybarrios/vllm-mlx/blob/v0.6.0/docs/reference/cli.md), [continuous batching guide](https://github.com/waybarrios/vllm-mlx/blob/v0.6.0/docs/guides/continuous-batching.md), local config read 2026-11-14; sources reviewed 2026-11-14.)

```bash
uvx --from vllm-mlx==0.6.0 vllm-mlx serve "{model}" \
  --served-model-name "{served}" --host 127.0.0.1 --port "{port}" \
  --gpu-memory-utilization 0.45 --max-kv-size "{ctx}" \
  --max-request-tokens 8192 --max-tokens 8192 \
  --continuous-batching --max-num-seqs 4 --prefill-step-size 512 \
  --cache-memory-mb 2048 --stream-interval 1 \
  --enable-auto-tool-choice --tool-call-parser "{tool_parser}"
```

The 8,192-token output ceiling is a proposed safety setting for this 64 GB H2H, not a measured optimum; it leaves room within the 16,384-token Gemma and 32,768-token Nemotron/Qwen contexts for the 6,000-token prefill. Use `--reasoning-parser qwen3` and remove any server default that disables thinking for Qwen3.8. For the Nemotron native MTP arm, add `--enable-mtp --mtp-num-draft-tokens 1` (one is the default); do not use `--mtp-optimistic`, which skips acceptance checks and is documented to allow roughly 5–10% wrong tokens. MTP generation remains on the OpenAI streaming endpoint; with `--stream-interval 1`, chunks are emitted immediately, though the exact local Nemotron-MTP stream was not tested. Native MLLM MTP is documented separately and falls back to normal decoding outside its greedy single-request envelope. A streaming client must request `stream_options.include_usage=true` to receive the final usage chunk. ([v0.6.0 CLI source](https://github.com/waybarrios/vllm-mlx/blob/v0.6.0/vllm_mlx/cli.py), [continuous batching guide](https://github.com/waybarrios/vllm-mlx/blob/v0.6.0/docs/guides/continuous-batching.md), [tool-calling guide](https://github.com/waybarrios/vllm-mlx/blob/v0.6.0/docs/guides/tool-calling.md), reviewed 2026-11-14.)

### Version-specific risks, token and memory reporting, and operability

The Qwen3.8 bare-Hub-ID engine-selection bug remains open in vllm-mlx issue #748: the issue says a bare repo ID can miss the `Qwen3.8` pattern and route to the wrong engine. The local H2H uses a filesystem path, which avoids the reported bare-ID condition; keep using that path. The v0.6.0 release includes fixes for streamed tool-call duplication, schema-aware streamed arguments, Qwen whitespace, prefix-cache ownership/replay, and prompt-token accounting on MLLM routes, so do not apply older pre-0.6 bug reports to this pinned release without checking their fix status. ([issue #748](https://github.com/waybarrios/vllm-mlx/issues/748), [v0.6.0 release](https://github.com/waybarrios/vllm-mlx/releases/tag/v0.6.0), issue/release state reviewed 2026-11-14.)

The OpenAI-compatible completion response provides `usage.prompt_tokens`, `usage.completion_tokens`, and `usage.total_tokens`; streaming needs `stream_options.include_usage=true` for the final usage-only chunk. `--enable-metrics` exposes Prometheus metrics at `/metrics`. `/v1/status` telemetry and fields such as `metal.active_memory_gb` and `metal.peak_memory_gb` are reported in upstream issue #442; treat them as issue-reported fields whose exact v0.6.0 payload still needs a canary. That issue also reports RSS and MLX cache counters understate active Metal memory, so pair engine counters with system-wide `vm_stat`/memory-pressure readings. ([v0.6.0 README](https://github.com/waybarrios/vllm-mlx/blob/v0.6.0/README.md), [issue #442](https://github.com/waybarrios/vllm-mlx/issues/442), reviewed 2026-11-14.)

Operability: **expert-friendly, not turnkey**. It has a short `uvx` launch path and convenient parser/metrics support, but candidates still require MLX artifact compatibility, correct MLLM routing for Qwen3.8, memory budgets, and family-specific thinking/parser choices. Pin the release because it tightly constrains the `mlx-lm` range. ([v0.6.0 release](https://github.com/waybarrios/vllm-mlx/releases/tag/v0.6.0), reviewed 2026-11-14.)

### Shared 64 GB argv, cache, and streaming

For a plain cell, use the v0.33 upstream launch shape with the local `0.45` budget from the current registry, plus the two scheduler caps below. Metal's `--gpu-memory-utilization` sizes paged-KV capacity rather than the whole runtime; weights, activations, and workspaces also consume unified memory. Keep automatic KV sizing instead of pinning `--kv-cache-memory-bytes` without a fresh residency measurement. The proposed `--max-num-batched-tokens 4096` is a conservative chunked-prefill limit for the configured 6,000-token prompts; `--max-num-seqs 4` caps concurrent rows. Cache policy is explicit per family: off for Nemotron-H, off for the H2H Qwen3.8 plain and speculative arms based on the community GDN report (the vendor labels hybrid prefix cache experimental), and on for Gemma4. A standalone high-throughput Qwen community profile uses `.75`, 8,192 batched tokens, and up to 8 sequences at 32k; the existing config comment records that `.70` caused 7.4 GB swap beside the running stack on 2026-11-13 and selects `.45` for the shared-host H2H. That local comment is prior evidence, not a measurement made in this research task. ([v0.33 configuration](https://github.com/vllm-project/vllm-metal/blob/v0.33.0/docs/configuration.md), [v0.33 model matrix](https://github.com/vllm-project/vllm-metal/blob/v0.33.0/docs/supported_models.md), [community recipe](https://github.com/xdanny/qwen3.8-vllm-metal/blob/main/README.md), reviewed 2026-11-14; local `config/bench_engines.yaml` read 2026-11-14.)

### Version-specific risks, token and memory reporting, and operability

The existing local H2H record reports a Qwen3.8 load failure (`Unrecognized image processor`). The upstream Transformers report documents that error for Qwen3.8 processor metadata in older releases and records an upstream model-card correction, but the exact local snapshot has not been refreshed or re-read here. v0.33's support table is not proof that this exact on-disk snapshot loads. Keep both Qwen Metal cells excluded until a fresh local-path canary proves the processor and a chat completion. ([Transformers issue #48511](https://github.com/huggingface/transformers/issues/48511), [local H2H exclusion](../../tests/benchmarks/engine_h2h.yaml), read/reviewed 2026-11-14.)

Two Gemma4 parser issues are directly relevant to the requested JSON/tool route. Upstream vLLM issue #54256 remains open and reports that a tool call emitted immediately after the reasoning channel can be dropped by the engine parser. Issue #47906 reports bare scalar argument values returned as JSON strings, with reproduction through v0.30 and a fix PR still open in the issue state reviewed here. Treat tool-call correctness and schema types as canary gates even when the CLI accepts `gemma4`. ([issue #54256](https://github.com/vllm-project/vllm/issues/54256), [issue #47906](https://github.com/vllm-project/vllm/issues/47906), reviewed 2026-11-14.)

For memory, the v0.33 config describes lazy KV allocation and a startup `vm_stat` commit probe, but open Metal issue #1198 reports a 0.33-era M5 Pro case where the pool became resident after warmup while RSS and `phys_footprint` stayed small. Use `/metrics` for vLLM prompt/generation token counters and KV usage; use system-wide `vm_stat` compression/swap counters and memory pressure as the independent resident-memory evidence. Do not use Python RSS alone as total Metal residency. For all engines, the OpenAI response usage fields provide prompt/completion/total counts; streamed usage needs the client option above. ([v0.33 Metal configuration](https://github.com/vllm-project/vllm-metal/blob/v0.33.0/docs/configuration.md), [issue #1198](https://github.com/vllm-project/vllm-metal/issues/1198), [vLLM 0.33 metrics docs](https://docs.vllm.ai/en/v0.33.0/usage/metrics/), [per-request metrics](https://docs.vllm.ai/en/v0.33.0/features/per_request_metrics/), reviewed 2026-11-14.)

Operability: **medium-to-high expertise**. Homebrew provides a coherent, pinned install and the OpenAI frontend is familiar, but the operator still needs to manage MLX artifact formats, an experimental MoE/Mamba family, parser registration, Metal memory headroom, hybrid cache limits, and greedy-only restrictions on speculative paths. A community Qwen3.8 recipe reports tested startup and short-request throughput on M5 Pro 64 GB, using a pinned target revision, custom chat template, and `qwen3_xml` tool parser. It does not pin the vllm-metal release in its README or prove the current local artifact/template combination; the H2H processor failure still needs a canary. ([v0.33.0 release](https://github.com/vllm-project/vllm-metal/releases/tag/v0.33.0), [community README](https://github.com/xdanny/qwen3.8-vllm-metal/blob/main/README.md), [community serve script](https://github.com/xdanny/qwen3.8-vllm-metal/blob/main/scripts/serve.sh), reviewed 2026-11-14.)
