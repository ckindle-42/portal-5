## How to read "faster than oMLX"

One published head-to-head against oMLX was found for these seats, and it is not this host. `https://rapidmlx.com/compare` (page dated 2026-09-27, measurement note 2026-10-12): Mac Studio, M5 Max, 36 GB, single run, same weights. Qwen3.8-27B 4-bit, Rapid-MLX 0.16.1 default (MTP, text lane) 37.9 tok/s one stream and 82.8 tok/s across four streams; oMLX 0.7.0 with its SSD cache 25.3 and 75.3; LM Studio MLX 26.0 and 69.7. The page says differences under about 5% are within run-to-run variation. That build is nine minor releases behind the registry pin 1.0.2.

mlx-serve's ladder against "oMLX's Lightning MTP" is a different model. `https://mlxserve.com/speculative-decoding/` image alt text, read 2026-11-14: "Native MTP context ladder: mlx-serve vs oMLX and MTPLX on Qwen 3.6 27B", v26.7.12, cold prompts 0.5K–64K, "+15–52%" on "oMLX's own oQ4e checkpoint". "Lightning MTP" on that page is oMLX's MTP feature name. It is not NVIDIA Nemotron 3.5 Lightning. Do not apply that percent to daily-moe or to Qwen3.8.

The marketing sentence on the same page says speculation is byte-identical. `https://github.com/ddalcu/mlx-serve/blob/main/docs/known-issues.md` (main, read 2026-11-14) limits that. Quality cells keep speculation off. Speed cells expect token differences where the contract says so.

## mlx-serve (ddalcu)

Sources read 2026-11-14: `https://github.com/ddalcu/mlx-serve` README (raw main), `docs/cli.md`, `docs/api.md`, `docs/known-issues.md`, `benchmarks.md`, `https://mlxserve.com/speculative-decoding/`, Hugging Face cards `ddalcu/Qwen3.8-27B-MLX-Serve-8bit` and `…-4bit`. Release tag `v26.11.2` published 2026-11-06. The README speed table is labeled v26.11.1. `benchmarks.md` has a 26.11.2 column. The registry pin matches the latest tag. Do not assume a later tag.

Install line in the README: `brew tap ddalcu/mlx-serve` then `brew install mlx-serve` for the CLI. The cask is the app. The app needs macOS 26.2. Default listen is `http://localhost:11234`. README: any supported MLX architecture, and any GGUF through embedded llama.cpp.

### 1. Variant per seat

README memory table: 16 GB suggests Gemma 4 E4B; 32 GB suggests Qwen 3.8 27B; 36 GB the 6-bit; 48–64 GB Qwen 3.8 27B 8-bit; 96 GB and up Flash-Next. On a 64 GB Mac the vendor's own pick for the coding family is the 8-bit pack, not the 4-bit.

**Coding (Qwen3.8 27B, dense).** The speed artifact is a checkpoint that actually contains the MTP head.

- Vendor pack: `ddalcu/Qwen3.8-27B-MLX-Serve-8bit` (card read 2026-11-14). 31.2 GB on disk, affine 8-bit group 64, native MTP head in the trunk shards, "loads it with no flags". The card says pick this if it fits, and pick 4-bit for a 32 GB Mac. That matches the README 48–64 GB row.
- Smaller vendor pack: `ddalcu/Qwen3.8-27B-MLX-Serve-4bit`, 18.2 GB, MTP included. Card table, same machine (M4 Max 128 GB, macOS 26.5, temp 0): 4-bit MTP-on code 75.3 tok/s versus 8-bit 53.6 tok/s, with weight noise 9.25% versus 0.71%.
- Our `Qwen3.8-27B-4bit` is the wrong speed artifact. `text.mtp_num_hidden_layers` is 1 and the index has zero MTP tensors. Auto-MTP has nothing to load.
- Our `Qwen3.8-27B-oQ4e-mtp` does have the head (`language_model.mtp.*`). The speculative page says an oMLX oQ checkpoint with the MTP head baked in is auto-loaded. That sentence was written about Qwen 3.6/3.8 MTP checkpoints, not proven here by a load.
- Our `Qwen3.8-27B-DFlash2` is a separate drafter (`DFlash2DraftModel`). The registry spec cell already points mlx-serve at it with `--drafter` and MTP/PLD off. `benchmarks.md` labels the ddalcu Qwen3.8 27B 4-bit column `dflash` from 26.10.1 onward (M4 Max) and on the M5 Ultra 26.11.2 cell (243 dflash). DFlash is a real vendor speed path for this family. It is not the 8-bit MTP pack the 64 GB row names.
- iQ-MLX 3.8 bpw is in `benchmarks.md` (M4 Max 26.11.2: 60 mtp) and is slower there than the ddalcu 4-bit history. It is not the 64 GB pick.

**daily-moe (Nemotron 3.5 Lightning 30B-A3B, MoE).** `docs/models.md` was not re-fetched in full this pass. The speculative page's MTP section names Qwen 3.6/3.8 and "an oMLX oQ checkpoint with its MTP head baked in". Our dir is an oQ-style mixed 4-bit pack (93 overrides) with 16 `mtp.layers.0.*` tensors and `num_nextn_predict_layers: 1`. Whether the `nemotron_h` plugin treats that key the way Qwen's `mtp_num_hidden_layers` is treated was not proven by a load. The rapid-mlx eligibility failure (below) is a different engine. Keep this dir for the mlx-serve speed try. Do not swap it for `mlx-community/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-4bit` without a separate decision: that is rapid-mlx's alias target, a different quant, and it is not on the path we inspected.

**Hunt (Gemma 4 26B-A4B QAT, MoE).** Keep `gemma-4-26b-a4b-it-QAT-4bit`. Vendor speed tables measure "Gemma 4 26B-A4B, 4-bit", which matches the non-QAT dir also on disk (`mlx-community--gemma-4-26b-a4b-it-4bit`), not the QAT symlink. Swapping would change the model. The CLI drafter example is `gemma-4-E4B-it-assistant-bf16` (`https://mlxserve.com/speculative-decoding/`). A 26B-A4B QAT assistant pack was not named on that page. `known-issues.md` says gemma4 drafted output is not exact (Gemma drafter and PLD). No assistant dir is on disk. The registry comment says do not download one. Leave hunt spec null for a quality cell. A speed cell can leave PLD on, and must expect divergence.

**Task-router (Gemma 4 E4B GGUF).** This is the one seat whose registered artifact mlx-serve can serve as-is: README says any GGUF. The recommended MLX chat model in the 16 GB row is Gemma 4 E4B 4-bit, which is different weights from the obliterated Q4_K_M GGUF. Do not replace the router seat with that MLX id if the comparison is the seated GGUF. `--llama-mtp-drafts 0` is the GGUF MTP off switch (`docs/cli.md`). `--no-pld` may not disable GGUF speculation: `known-issues.md` says the llama adapter ignores `Request.no_drafts`.

### 2. Launch flags on 64 GB

From `docs/cli.md` on main, read 2026-11-14. Defaults in parentheses.

- `--ctx-size N` (auto from GPU memory). Pin the seat: 32768, 32768, 16384, 2048. Do not leave auto. The checkpoints declare 262144.
- `--prefill-chunk N` (8192). Lower only if a load fails on prefill peak. Not a speed default.
- `--kv-quant {off,4,8}` (off). Leave off on 64 GB for a quality or speed cell. The flag exists to spend about a decode tax for KV RAM. The percent was not copied from `docs/performance.md` this pass; do not invent it. `--kv-attn-mode {auto,dense,fused}` (auto) only applies when KV quant is 4 or 8. `known-issues.md`: `--kv-attn-mode fused` is a silent no-op on Gemma 4. Do not set it on hunt.
- `--prefix-cache-mem` (2 GB, or one session at the working context on hybrid models including Qwen3.5+ and Nemotron-H). Qwen3.8 and Lightning fall in that hybrid note. `--prefix-cache-disk` (off). Leave disk off for a bench so a restart is cold.
- `--max-resident-mem` (auto = GPU working set). `--max-resident-models` (3). A one-model bench does not need a tighter cap unless the orchestrator wants a hard ceiling under 64 GB. `--idle-evict-secs` is off.
- `--max-concurrent N` (1). Concurrent requests batch-decode anyway; the flag sizes the queue (N+32) and how many decoders a long prefill admits. Keep 1 for single-stream. Raise it only to reproduce a four-chat number.
- Spec: `--pld` / `--no-pld` (on). `--no-drafter` (off, meaning a shipped drafter does load). `--no-mtp` / `--mtp` (on when a head is loaded, Metal). Priority described on the speculative page: MTP when the head is present, else a drafter, else PLD. Per request: `enable_pld`, `enable_drafter`, `enable_mtp`.
- Streaming: the speculative page says speculation runs on chat, Anthropic messages, Responses, and legacy completions, streaming and non-streaming, tools or not. `known-issues.md` still lists a streaming gate gap: a bare Hermes `<function=` opener can leak. Streaming does not turn speculation off. It is not a proof that tool streams are clean.
- `--reasoning-budget N` (-1 unlimited, 0 no thinking). For a think-off cell pass 0. The 8-bit card also documents per-request `"enable_thinking": false` and `reasoning_effort` of `xhigh` / `medium` / `low` (Qwen3.8 vocabulary, default `xhigh`). There is no `--reasoning-parser` flag in the CLI table that was read.
- `--no-tool-autocorrect` turns off schema repair. There is no `--tool-call-parser` name in that CLI table. The 8-bit card says Qwen3.8 tools are XML (`<tool_call><function=name><parameter=key>`) and mlx-serve repairs them into OpenAI `tool_calls`. Our registry `tool_parser: hermes` is a rapid-mlx/vLLM flag. It is not an mlx-serve argv field.
- `--no-vision` disables the vision encoder. Text benches should pass it on Qwen3.8 and Gemma 4, which are conditional-generation packs.
- `--warmup-full` (off). The CLI text says strongly recommended when benchmarking. The first load then compiles a ladder of prompt sizes before ready.
- `--metrics` (off) exposes `GET /metrics` and `GET /metrics.json`. Metric names were not copied.
- GGUF only: `--llama-cache-entries N` (4). Each entry holds a full `--ctx-size` of KV from load. Pin 1 on the 2048-token router. `--llama-mtp-drafts N` (2). `0` turns GGUF MTP off. `--llama-kv-quant {off,q8,q4}` (off).

Quality-plain (current registry shape, plus the bench flags that do not change the off-spec contract):

```text
mlx-serve --serve --model {mlx_root}/{model_dir} --host 127.0.0.1 --port {port}
  --ctx-size {ctx} --no-pld --no-drafter --no-mtp
  --no-vision --warmup-full --prefix-cache-disk off
  --reasoning-budget 0
```

Drop `--no-vision` if the seat must accept images. Drop `--reasoning-budget 0` if the seat must think. For the GGUF router, also pass `--llama-mtp-drafts 0 --llama-cache-entries 1`, and do not trust `--no-pld` alone (`known-issues.md`).

Vendor-fast, coding, once the 8-bit dir is on disk (it is not today; downloading is out of this lane):

```text
mlx-serve --serve --model {mlx_root}/Qwen3.8-27B-MLX-Serve-8bit
  --host 127.0.0.1 --port {port} --ctx-size 32768
  --no-vision --warmup-full --kv-quant off --prefix-cache-disk off
```

Leave PLD/MTP/drafter at defaults so the baked head loads. If 31.2 GB of weights plus a 32768 KV cache does not fit beside the OS, use the 4-bit ddalcu dir the same way, or the on-disk 4-bit plus `--drafter {mlx_root}/Qwen3.8-27B-DFlash2 --no-pld --no-mtp`. The oQ4e-mtp dir is the third local candidate: `--mtp --no-pld --no-drafter`.


A load failure is an acceptable result. Do not pass `--force` anything. There is no such flag in the table that was read.

### 3. Bugs, tokens, resident memory

`known-issues.md`, main, 2026-11-14:

- `qwen3_5` `exact_drafted` is yes only for dense affine packs with a DFlash drafter bound and every trunk projection inside the row kernels. Not MoE, not `qwen3_next`, not Hadamard, not bf16. Our coding model is dense affine `qwen3_5`. MTP-on exactness is not that row. The known-divergence list includes `qwen3_5` MoE and bf16, and `gemma4` (Gemma drafter, PLD).
- `nemotron_h` drafted is "yes, as `qwen3_5`", and "a pack outside the row kernels serves plain kernels with the flag set and is not exact". Lightning is MoE (`num_experts_per_tok` 6). Do not claim Lightning MTP is byte-exact.
- `gemma4` drafted: no. Resumed: yes, greedy, through an SSD restart.
- `exact_concurrent` is declared by no plugin.
- Embedded llama.cpp: contracts unverified. Adapters ignore `Request.no_drafts`, so a drafted check cannot see a GGUF draft. Special-token injection on GGUF is still open (fixed only on the MLX chat path).
- Bare `Infinity` in some Nemotron Nano `config.json` is refused. Not checked against our Lightning config.
- A loop cut inside a buffered tool call delivers nothing.
- Streaming gate: a bare Hermes `<function=` can leak.
- `--kv-attn-mode fused` is a silent no-op on Gemma 4.

GitHub, read 2026-11-14:

- `ddalcu/mlx-serve` issue 1079 is open. Title: "26.11.1: retained prompt/session cache never released — idle floor ratchets to the arena ceiling". Updated 2026-11-14. `known-issues.md` did not name this ratchet. Whether 26.11.2 fixed it is unknown while the issue stays open. A long bench should watch resident memory, not assume the process returns to its idle floor.
- Issue 831 is closed 2026-10-15: agentic repetition under `--mtp-typical` / `--mtp-greedy-tail`. Those flags are off by default (`--mtp-greedy-tail` default off in `docs/cli.md`). Do not turn them on for this bench.

Tokens (`docs/api.md`): chat usage always carries `prompt_tokens_details.cached_tokens`, and `completion_tokens_details.reasoning_tokens` when the reply reasoned. Streamed usage is on the `stream_options.include_usage` chunk. `/api/ps` exists as an Ollama wire. Which memory fields it fills was not copied from source. Resident memory the engine documents is `--metrics` (`GET /metrics`, `GET /metrics.json`). Process RSS is the OS. It is not an HTTP field confirmed here.

### 2. Launch flags on 64 GB

From perf-flags (page says 1.0.3) and the changelog.

- Prefix cache: on for every model. Off with `--disable-prefix-cache`. `--cache-memory-mb N` default "about 20% of RAM". `--hybrid-cache-entries N` default 0. Qwen3.8 and Nemotron-H are hybrid. Gemma 4 is called out as sliding-window, and the same flag covers it. Default 0 means a stable system prompt is re-prefilled unless the orchestrator sets N. `--pin-system-prompt` is off.
- `--no-spec-decode` turns off MTP and every other speculative method, including an alias's default MTP. The current plain cell is the quality cell. The speed cell for coding drops it only when the model is the MTP alias (or a local dir that actually has the head). Dropping it on our tensor-less 4-bit is not the vendor path.
- `--speculative-config` JSON. MTP fields include `num_speculative_tokens`. DFlash: `{"method":"dflash","model":"..."}`. Suffix: `{"method":"suffix","num_speculative_tokens":8}` and it "does not run on hybrid models", so not the Qwen3.8 or Lightning speed plan. Gemma assistant: name the assistant as the `"model"` of an MTP config. Not on by default.
- MTP runs one request at a time. A second request yields at a token boundary onto the ordinary batched path. Continuous batching of ordinary decode does not need a flag. The page does not say streaming disables speculation.
- KV: `--kv-cache-dtype {bf16,int8,int4}` default `bf16`. `--kv-cache-turboquant {v4,k8v4,none}` is alias-driven, `k8v4` on 9 verified Qwen3.5/3.6 aliases, not on the Qwen3.8 or Gemma or Lightning rows in that list. Sliding-window models (the page names Gemma 3/4 and GPT-OSS) reject an explicit `int8` / `int4` at startup. For a quality cell set `--kv-cache-turboquant none` and leave dtype `bf16`. For a speed cell leave the alias default.
- PFlash is off. It is lossy. Do not enable it for this bench. If it is on, `usage.prompt_tokens` still counts the prompt that was sent, and a streamed completion carries `metrics.prompt_compression` on the final chunk.
- `--enable-auto-tool-choice` is required with a parser. The yaml already passes it. Parsers to pass, from the catalog, not from our `auto` / `hermes` defaults: coding `qwen3_coder_xml` plus reasoning parser `qwen3`; hunt `gemma4` and reasoning `gemma4`; Lightning `nemotron` and reasoning `qwen3`. The CLI flag for the reasoning parser was not copied from `rapid-mlx serve --help` (the binary was not run). perf-flags `rapid-mlx info` sample prints "Reasoning parser". The orchestrator must take the flag spelling from `rapid-mlx serve --help` on the pinned build.
- Context length: no `--ctx-size` or `--max-model-len` was copied from these pages. Do not invent the flag. `rapid-mlx serve --help` on 1.0.2 is the check. Seat targets remain 32768 / 32768 / 16384 / 2048.
- `--trusted-hosts` stays, including `host.docker.internal`. The yaml comment is an operator finding: the DNS-rebinding guard returns 400 for a Host outside the allowlist, and the values replace the defaults.
- `--no-telemetry` is our fairness pin. It was not confirmed as the vendor default.
- Memory cap: changelog 1.0.3 upgrade note (2026-11-11): "Dynamic loading defaults to the smaller of 80% of physical RAM and 90% of Metal's recommended working set; explicit memory limits retain their behavior." That sentence is 1.0.3. Do not assume it on a 1.0.2 pin. On 64 GB, 80% is about 51 GB. An 8-bit 31 GB Qwen plus 32k KV might fit. That is arithmetic, not a measured load.
- 1.0.2 changelog: idle unload can keep the API up (Desktop). Eligible models download their pinned MTP head automatically on first `serve`. A bench that points at a local dir should not rely on that download. This lane must not download.

## Which seats are most likely to beat oMLX

Reasoned from the documents above. Not a measurement.

1. **Coding, rapid-mlx, vendor MTP alias.** This is the only seat with a published win against oMLX: 37.9 versus 25.3 tok/s on an M5 Max 36 GB, Rapid-MLX 0.16.1 versus oMLX 0.7.0, one run, MTP on. The registry cell cannot reproduce it. It serves `Qwen3.8-27B-4bit`, which has zero MTP tensors, with `--no-spec-decode` on the plain cell and an experimental 4-bit DFlash overlay on the spec cell. The comparable cell is alias `qwen3.8-27b-4bit`. Even then the hardware and the version differ. Likelihood is "best chance of the matrix", not "expected on this Mac".

2. **Coding, mlx-serve, ddalcu 8-bit or 4-bit with the baked head, or on-disk DFlash / oQ4e-mtp.** The vendor's 64 GB recommendation is the 8-bit pack (31.2 GB, MTP included). Published self-speedups are large (4-bit code 75.3 versus 26.3 on an M4 Max 128 GB). The published versus-oMLX ladder is Qwen 3.6 27B at v26.7.12, not this checkpoint. Our plain 4-bit with `--no-mtp` will not show that speedup. 8-bit decode on that M4 Max card is slower than 4-bit (53.6 versus 75.3) and is the quality pick, not the tok/s pick.

3. **daily-moe, mlx-serve, oQ4e with `--mtp`.** The tensors exist. The plugin's willingness to use `num_nextn_predict_layers` on a mixed oQ pack is unproven, and `known-issues.md` does not give MoE `nemotron_h` a byte-exact draft contract. rapid-mlx will not run MTP on this pack. mlx-lm will not use the head. If oMLX production is already `mtp_enabled` on this same dir, mlx-serve has to beat that path, and no Lightning number versus oMLX was found. Likelihood is lower than coding, and a failed load is plausible.

4. **Hunt, either engine, PLD or a future assistant.** Gemma 4 drafts and PLD are a known mlx-serve divergence, so a faster hunt cell can fail a byte match. No oMLX column was found for Gemma 4 26B QAT. The rapid-mlx 72.6 tok/s figure is an M4 Pro 48 GB "Gemma 4 26B" number with no oMLX beside it. Keep QAT. Do not expect a clean win.

5. **Task-router.** Only mlx-serve can serve the seated GGUF. Beating oMLX on this seat is the wrong question if production routing is the GGUF on Ollama. An MLX E4B on rapid-mlx or mlx-lm is a different model (the catalog's `gemma-4-e4b-4bit`, or mlx-serve's 16 GB suggestion). Report it as a different seat if it is tried.

6. **mlx_lm.server on every spec seat.** Least likely. No MTP, the project tells you not to use it in production, streamed turns do not fill the prompt cache (issue 1802, still open), and the tool-call drop fixed on 2026-11-09 is newer than wheel 0.32.2.
