## KV cache — the corrected methodology finding

The 2026-04/05 protocol used a ~120–190-token prefix. oMLX 0.5.x's paged cache operates on **256-token blocks**, so a sub-block prefix can never produce a hit. On the legacy short-prefix cell, warm TTFT is still flat-to-slightly-worse (0.35→0.42s on 3B) — exactly the old signature — while the agentic-long cell (realistic persona + tool-schema system prompt, ~3K tokens) shows the feature working as advertised. Part of the original "broken KV cache" verdict was a **methodology artifact**: the feature may have been fixed for block-sized prefixes earlier than this run. Ollama comparison (gemma, agentic-long): cold 7.395s, warm 1.794–2.442s — llama.cpp slot caching works within a loaded model, but oMLX wins cold prefill (2.8s vs 7.4s, ~2.6×) and warm TTFT (0.79s vs ~2.1s), and its cache additionally persists to SSD across restarts and is shared block-wise across conversations.

## Environment anomalies encountered (all resolved; watch-items for Phase 1)

1. **xgrammar broken after `brew reinstall --with-grammar`** — the formula's `patch_xgrammar` post-install did not leave a working install on this machine (upstream jundot/omlx#1005 class: deleted dist-info `RECORD` + missing rpath). Fixed manually: `install_name_tool -add_rpath <site>/tvm_ffi/lib <site>/xgrammar/libxgrammar_bindings.dylib` + `codesign -s -` + RECORD entry. **Any brew reinstall/upgrade of omlx must re-verify `python -c "import xgrammar"` and `GrammarCompiler initialized` in `~/.omlx/logs/server.log`.**
2. **Restart-by-pattern fails** — the server process is `omlx-server`, so `pkill -f "omlx serve"` matches nothing. The v3 MTP gate initially ran all six cells with MTP on because of this. Kill by port (`lsof -ti :8085`).
3. **MTP toggle verification** — `~/.omlx/model_settings.json` is honored at engine load; the "Speculative backend selected … (active)" line is emitted only when MTP engages, and only at first request (lazy engine load). Absence = inactive.
4. **Untagged Ollama GGUF defaults to max context** — `qwen3-coder:30b-a3b-q4_K_M` loads at 262,144 ctx (74 GB, 35% CPU offload, 3–15 t/s). Production `-ctx16k` tag: 22 GB, 100% GPU, ~59 t/s. This is P5-OLLAMA-OPTIONS-001 in action and is one of the frictions Phase 1 eliminates (oMLX per-model settings/profiles instead of derived tags).
5. **Dead symlinks** — 24 of 29 entries in `/Volumes/data01/omlx-models` were dangling symlinks into the cleaned `~/.cache/huggingface`. Cleanup pending (punchlist).
6. **Metal wired cap** — oMLX raised `iogpu.wired_limit_mb` to the kernel cap (47 GB) and recommends 58 GB (`sudo sysctl iogpu.wired_limit_mb=59392`). Not applied (sudo, persistent); 47 GB sufficed for all gates. Optional for Phase 1 co-residency.
7. **Vendor debug patch left in place** — `omlx/engine/batched.py` gained a `PHASE0-DEBUG` warning traceback on grammar-init failure (wiped by any brew reinstall; harmless).

## Judgment questions (carried from prior rounds)

**Q1: Did warm TTFT beat cold this time?** YES — 3.5–7.0× on agentic-length prefixes with direct `cached_tokens` evidence. The cancel trigger is cleared on the path that matters; the legacy short-prefix cell remains flat (256-token block floor).

**Q2: Is the practical speedup over the production 4-bit baseline still marginal (0.95–1.14×)?** NO — 1.32–1.46× decode on the production primary before speculation, 2.2–2.5× with MTP, plus a 2.6× cold-prefill advantage and a 3–7× warm-prefix advantage. The May baseline comparison was against the retired mlx-proxy; the correct current comparison is production Ollama GGUF, and oMLX beats it everywhere measured.

**Q3: Can it serve the production families' tool contracts?** MOSTLY — Qwen and Gemma parse correctly; Llama-family bare-JSON tool output does not parse (Ollama handles it). Impact: none of the current production primaries are Llama-family; dolphin-llama3:8b and Llama-3.2-3B-instruct entries in `backends.yaml` would be affected if migrated.

## Recommendation

**PROCEED to Phase 1** — dual-backend integration with oMLX as the Apple-Silicon primary tier and Ollama as fallback, per the 2026-08-02 plan. Suggested Phase-1 scope guards:

- Router model stays on Ollama initially, OR migrates to a dedicated always-grammar oMLX instance (the gemma livelock requires an unconstrained→constrained transition, which a router-only workload never produces).
- Migrate `auto-coding` (+laguna variant — oMLX natively accelerates Laguna) and `auto-security` primaries first; keep the two GGUF-only security fine-tunes (P5-MLX-EVAL-005), phi4-reasoning-plus (GGUF crash refugee — but note `Phi-4-reasoning-plus-MLX-4bit` exists in the omlx-models cache and is worth a Gate-6 probe), and qwen3-coder-next on Ollama until probed.
- Do not migrate Llama-family models until their tool output parses.
- File upstream: (a) gemma grammar livelock sequence bug; (b) xgrammar brew patch gap (#1005 follow-up).
- Version-pin omlx in Phase 1; upgrades gated through this harness + `smoke_stream.sh`.
