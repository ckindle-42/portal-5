## Correction: Part D's first-pass verdict was wrong, root-caused mid-task

The first bench pass on `bench-deepwen-cad` showed TPS 40.4 t/s (clears the floor) but Q-score
0.00 — 2/5 generic-prompt runs empty, one with garbled mid-stream Unicode injection, and the
real CAD tool loop degenerating into unrecoverable token garbling with malformed tool-call XML.
This was initially written up and committed as "declined — the Q4.5-MoQ GGUF conversion is
broken at generation time." **That conclusion was wrong**, caught by a direct question during
review ("was it a template issue as we've seen before?", referencing the Antares finding in V1
where raw completion was coherent but chat-templated requests produced garbage).

Isolating with the same raw-vs-templated method used for Antares: raw completion was perfectly
coherent. So was simple chat, and even chat with the full tool schema + `tool_choice: required`
— when tested directly against Ollama. The garbling only reproduced through the actual pipeline.
Root cause, found via the pipeline's DEBUG log: **`P5-OLLAMA-OPTIONS-001`**, an *already-documented*
`KNOWN_LIMITATIONS.md` entry — Ollama's OpenAI-compatible `/v1/chat/completions` endpoint (what
the pipeline uses) silently ignores the entire `options` sub-object, so `bench-deepwen-cad`'s
`context_limit: 8192` had zero effect. The model ran at whatever context was already loaded,
which corrupted tool-call JSON generation. `auto-cad` itself already works around this exact,
documented limitation — its `model_hint` is a pre-baked `-ctx8k` tag, not a bare model name.
**This workspace's initial setup should have checked `KNOWN_LIMITATIONS.md` before creating a new
`context_limit`-bearing eval workspace, per CLAUDE.md's own instruction, and didn't.**

Fixed via the documented `./launch.sh apply-model-params` command (which itself required
`PORTAL_ENABLE_EVAL=1` to see eval-module workspaces at all — the first attempt silently
processed zero workspaces without it), producing `portal5/deepwen-3.6:q4.5-moq-ctx32k` and
updating `model_hint` automatically. Re-testing post-fix: the model's reasoning is genuinely
coherent and technically correct on both CAD sub-tasks, but it never converges to a tool call
under the full production request shape (`finish_reason: stop` after 3346-5858 completion
tokens, not truncation) — a real, different, more precise finding than the retracted one.
The verdict stays **declined** for this lane, but the reasoning behind it is now accurate.

## Speculative-decoding findings

Ollama's MLX engine (0.32.7) does provide DFlash natively for Muse-Glimmer — this was measured
directly, not assumed. A controlled same-prompt A/B (8 runs per arm, `draft_num_predict` 15 vs 0)
found only a **1.9% decode-TPS delta** (20.38 vs 19.99 t/s, both within one stdev of each other),
nowhere near the card's claimed 1.5-1.8x on M4/M5. Output was bit-identical across all 16 runs
(8 on, 8 off) and between the two arms, so spec-decode correctness holds — it just doesn't buy
real speed on this serving path today. Jackrong's MTP (GGUF/llama.cpp path) could not be measured
at all: `ollama show`'s Parameters section lists no `draft_num_predict`-equivalent for this
architecture, and the option is silently ignored rather than erroring — so unlike DFlash, this is
an **undetermined** result, not a second negative data point. Combined verdict: on the one path
that could be controlled-A/B'd, spec-decode is not currently worth leaning on post-mlx-proxy-
retirement for real throughput gains, though correctness is unaffected either way.

## What actually happened vs. what the task file assumed

- **Part A**: hit a real, permanent infra ceiling while loading Muse-Glimmer — `OLLAMA_GPU_OVERHEAD`
  was fixed at 40GiB in `/Library/LaunchDaemons/com.portal5.ollama.plist`, capping any single Ollama
  model at ~15.5GiB regardless of oMLX's actual state (a static Metal working-set carve-out, not
  live memory pressure — confirmed by testing that freeing oMLX's loaded models and even a full
  daemon restart via `launchctl kickstart -k` left the number completely unchanged). Root-caused to
  `launchctl kickstart -k` not re-reading the plist's `EnvironmentVariables` — only a full
  `bootout`/`bootstrap` cycle does. Fixed permanently by lowering to 20GiB (real oMLX coexistence
  headroom without starving Ollama); this is a box-level fix, not scoped to this bench, and is now
  recorded in `KNOWN_LIMITATIONS.md` (`P5-OLLAMA-GPU-OVERHEAD-001`) so it doesn't get re-diagnosed
  from scratch by a future session. This is a genuinely new limitation (not previously documented).
- **Part B**: Jackrong's 9B GGUF pulled clean with the task's literal `hf.co/...` reference — no
  workaround needed, unlike several V1 candidates. The 4B's bare repo turned out to be
  safetensors-only as the task anticipated; found the official `-MTP-GGUF` mirror repo rather than
  giving up, standard tag naming, no puller issues.
- **Part D**: `ollama pull hf.co/quimmedes/Deepwen-3.6:Q4.5-MoQ` and `:BF16` both 400'd — confirmed
  this is Ollama's puller rejecting the uploader's custom "MoQ" quant-scheme naming (not a network
  or gating issue; the repo is public). The no-tag pull hangs indefinitely rather than erroring.
  Worked around via direct `huggingface_hub.hf_hub_download` + `ollama create` (GGUF metadata
  auto-parsed cleanly, no hand-written Modelfile needed). Then hit — and initially misdiagnosed,
  then correctly root-caused — `P5-OLLAMA-OPTIONS-001`, see the correction section above. This one
  was an existing, already-documented limitation this task's setup should have consulted first.
