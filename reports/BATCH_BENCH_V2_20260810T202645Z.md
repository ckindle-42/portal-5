## Correction: Part D went through three verdicts before landing on the right one

**First pass**, committed: TPS 40.4 t/s (clears floor) but Q-score 0.00, garbled tokens, malformed
tool-call XML on the real CAD gauntlet — written up as "declined — the Q4.5-MoQ GGUF conversion is
broken at generation time." **Wrong**, caught by "was it a template issue as we've seen before?"
(referencing V1's Antares finding — raw completion coherent, chat-templated requests garbage).
Root-caused to `P5-OLLAMA-OPTIONS-001`, an *already-documented* `KNOWN_LIMITATIONS.md` entry:
Ollama's `/v1/chat/completions` endpoint (what the pipeline uses) silently ignores the whole
`options` sub-object, so `context_limit: 8192` had zero effect and the model ran at whatever
context was already loaded, corrupting tool-call JSON. `auto-cad` already works around this
exact limitation with a pre-baked `-ctx8k` tag — this workspace's setup should have checked
`KNOWN_LIMITATIONS.md` first and didn't. Fixed via `./launch.sh apply-model-params`
(`PORTAL_ENABLE_EVAL=1` required), producing `portal5/deepwen-3.6:q4.5-moq-ctx32k`.

**Second pass**, also committed: with `tool_choice: required` still set (cloned from `auto-cad`
without verifying fit), the model produced long, coherent, technically correct reasoning but never
converged to a tool call — 0/2 on both sub-tasks. Written up as "declined — genuine tool-call-
convergence failure." **Also wrong** — not the full story — caught by a direct challenge that the
model likely has real value and tool exposure hadn't been run to ground.

**Third pass**: removed `tool_choice: required`, left at Ollama's default `auto`. The model
converges reliably-enough and produces genuine output: one OpenSCAD sample independently compiled
via `openscad --render` to a real 97.7KB STL (288 vertices, 156 facets, rounded-corner hulls,
counterbored standoffs, dimensional `echo()` diagnostics — more sophisticated than a basic box);
the trimesh sub-task converged to correct gyroid-surface implicit-function code via marching
cubes. An 8-run repeat of the identical production request (live tool schema from
`tool_registry.get_openai_tools()`, `tool_choice: auto`) measured **4/8 convergence** — real,
moderate unreliability, not a hard failure. A same-size incumbent spot-check wasn't confidently
better (one apparent `auto-cad` "failure" was a detection-heuristic miss on inspection, not a
true failure). **Final verdict: pass, with real caveats** — both earlier declines are retracted.

## Speculative-decoding findings

Ollama's MLX engine (0.32.7) does provide DFlash natively for Muse-Glimmer — this was measured
directly, not assumed. A controlled same-prompt A/B (8 runs per arm, `draft_num_predict` 15 vs 0)
found only a **1.9% decode-TPS delta** (20.38 vs 19.99 t/s, both within one stdev of each other),
nowhere near the card's claimed 1.5-1.8x on M4/M5. Output was bit-identical across all 16 runs
(8 on, 8 off) and between the two arms, so spec-decode correctness holds — it just doesn't buy
real speed on this serving path today. Jackrong's MTP (GGUF/llama.cpp path) could not be measured
at all: `ollama show`'s Parameters section lists no `draft_num_predict`-equivalent for this
architecture, and the option is silently ignored rather than erroring — so unlike DFlash, this is
an **undetermined** result, not a second negative data point. Combined verdict: on the one path
that could be controlled-A/B'd, spec-decode is not currently worth leaning on post-mlx-proxy-
retirement for real throughput gains, though correctness is unaffected either way.

## What actually happened vs. what the task file assumed

- **Part A**: hit a real, permanent infra ceiling while loading Muse-Glimmer — `OLLAMA_GPU_OVERHEAD`
  was fixed at 40GiB in `/Library/LaunchDaemons/com.portal5.ollama.plist`, capping any single Ollama
  model at ~15.5GiB regardless of oMLX's actual state (a static Metal working-set carve-out, not
  live memory pressure — confirmed by testing that freeing oMLX's loaded models and even a full
  daemon restart via `launchctl kickstart -k` left the number completely unchanged). Root-caused to
  `launchctl kickstart -k` not re-reading the plist's `EnvironmentVariables` — only a full
  `bootout`/`bootstrap` cycle does. Fixed permanently by lowering to 20GiB (real oMLX coexistence
  headroom without starving Ollama); this is a box-level fix, not scoped to this bench, and is now
  recorded in `KNOWN_LIMITATIONS.md` (`P5-OLLAMA-GPU-OVERHEAD-001`) so it doesn't get re-diagnosed
  from scratch by a future session. This is a genuinely new limitation (not previously documented).
- **Part B**: Jackrong's 9B GGUF pulled clean with the task's literal `hf.co/...` reference — no
  workaround needed, unlike several V1 candidates. The 4B's bare repo turned out to be
  safetensors-only as the task anticipated; found the official `-MTP-GGUF` mirror repo rather than
  giving up, standard tag naming, no puller issues.
- **Part D**: three-pass correction, see above. `ollama pull hf.co/quimmedes/Deepwen-3.6:Q4.5-MoQ`
  and `:BF16` both 400'd — confirmed this is Ollama's puller rejecting the uploader's custom "MoQ"
  quant-scheme naming (not a network or gating issue; the repo is public). Worked around via
  direct `huggingface_hub.hf_hub_download` + `ollama create`. Two subsequent misdiagnoses (context
  limit, then tool_choice) both required a human prompt to catch — an honest miss in this task's
  own review discipline, corrected before the report was finalized rather than left standing.
