# W3 — cancellation end to end

**Disposition:** DONE (W3.1–W3.4). W3.5 REJECTED (evidence below). Live run 2026-10-07 14:37–14:47 UTC under [W3_watchdog.log](W3_watchdog.log): no trip; minimum memory free was 34%, pressure level 1.

## Defects found by the live test (not visible in mocks)

1. **`CorrelationIdMiddleware` hid every disconnect.** As a Starlette `BaseHTTPMiddleware` it wraps `receive` in a task group. Inside `Request.is_disconnected()`'s pre-cancelled scope, that wrapper never yields the `http.disconnect` message, so a handler behind it can never see its client leave. First live run: two non-streaming requests abandoned at 10 s and 12 s ran to completion on oMLX (1231 and 1084 tokens, 17.9 s and 15.6 s), and the cancel counter stayed at zero. Fix: rewrote it as pure ASGI. `test_disconnect_is_seen_through_the_pipeline_middleware_stack` drives the real middleware stack over raw ASGI; it fails on the old middleware and passes on the new one.
2. **The native passthrough blocked in `send()`.** A non-streaming Ollama call sends response headers only when generation ends. Live: Ollama was still generating (n_gen 1701 and climbing) 30 s after the client left. Fix: admit and send now run under `cancel_on_disconnect`.
3. **The load-guard lock could leak to a cancelled caller.** `admit` released the host-wide cold-load lock for `Exception` but not for `CancelledError`. A disconnect during admission would have deadlocked every later cold load, and W3's cancellation makes that path reachable. Fix: `admit` and `admit_omlx` release on cancel. Two tests fail on the old code and pass on the fix.

## W3.5 — council load-plan waves: REJECTED

The compliance council does not fan out. `run_council` asks its seats one at a time (`portal/modules/compliance/core/council.py`, the `for seat in seats` loop; the override pass is sequential too). Every seat's cold load already goes through the load guard, which serialises it, waits for memory, and sends `X-Portal-Load-Wait` sized by `COMPLIANCE_LOAD_WAIT_S=900` (W1). With no concurrency there is nothing to split into fit-sized waves, and a pre-flight `/admin/load-plan` would only predict what the guard already enforces per seat. Revisit trigger: if the council is ever made concurrent, add the plan-and-wave step in the same change. The sweep's optional concurrency (`COMPLIANCE_SWEEP_CONCURRENCY`, default 1) runs one model, so it is not a multi-model fan-out either.

## Scope note

Cancellation covers the REST tool route (`/tools/{name}`) that the pipeline and OWUI tool servers use. Calls over the MCP streamable-HTTP protocol go through the SDK's own request handling and are not covered here.

## W2 follow-up correction (landed with W3)

W2 had the pinned intent-router call (`routing._guarded_router_post`) run `LoadGuard.admit` as well as busy tracking. The task specifies tracking only, and admission added an `/api/ps` round-trip plus a new HTTP client to every routing decision, inside the router's deadline. It also made `test_router_timeout_schedules_one_uncancelled_reload` order-dependent under xdist (it failed in the W3 commit hook when an earlier test left `GUARD` set). The call is now tracked only (`GUARD.begin`).
