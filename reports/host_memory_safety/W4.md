# Host Memory Safety V1 — W4 live evidence

Captured 2026-10-07 on the live production Mac, arm64. The W4 implementation and evidence are in the working tree at this capture.

## Copy-truncate safety proof

The active `com.portal5.pipeline-mcp` LaunchAgent writes to `~/.portal5/logs/pipeline-mcp.log` through launchd `StandardOutPath` and `StandardErrorPath`. Before truncating it, its 1,027,613-byte, 2,112-block contents were copied to `/tmp/host_memory_safety_pipeline-mcp.before.log`. Truncating the existing file and requesting `GET /health` from the same service produced a 58-byte log with 8 allocated blocks, including the 200 response. This is consistent with append mode: the existing writer started at the truncated end instead of seeking to its previous offset and creating a sparse file. The saved contents and probe line were restored to the same log path; the restored file was 1,027,671 bytes with 2,008 blocks. The launchd job's configured stdout path and writer PID were checked with `launchctl print` and `lsof`.

The production Ollama daemon's `/Library/LaunchDaemons/com.portal5.ollama.plist` sets both stdout and stderr to `/opt/homebrew/var/log/ollama.log`. The oMLX service plist sets both to `/opt/homebrew/var/log/omlx.log`. No writer needed a restart fallback.

## Rotation implementation and first run

`scripts/rotate_logs.py` uses only the Python standard library. It reads `LOG_ROTATE_MAX_MB` (100 MiB default), `LOG_ROTATE_KEEP` (5 default), and optional semicolon-separated `LOG_ROTATE_FILES` from process environment or `.env`. The default set is Ollama, oMLX, and `~/.portal5/logs/*.log`. Snapshots are copied in bounded chunks, gzip CRC and total uncompressed size are checked before truncating, and late append-only bytes are added as additional gzip members. A changing inode, shrink, same-size mutation, copy error, or log growth that does not settle skips the source without truncating it. The source inode is preserved.

The first run safely skipped Ollama because the active file grew during the initial copy; the source remained untouched. The follow-up implemented tail capture for the append-only writer and a second pass succeeded. Before that run, `engine_autoupdate.busy()` returned `idle`, `ollama ps` showed one already-resident 5.4 GB model, memory pressure showed 87% free, swap free was 1,281 MiB, and `/opt/homebrew/var/log` had 357 GiB free.

The rotator returned:

```text
ROTATED /opt/homebrew/var/log/ollama.log: 3342355908 bytes; saved /opt/homebrew/var/log/ollama.log.1.gz
```

`ollama.log.1.gz` was 289,184,066 bytes and `gzip -t` passed. The active log stayed on inode `9283962`; after rotation it grew from 2,184 bytes / 8 blocks to 2,453 bytes / 8 blocks after a harmless `/api/version` request and `ollama ps`, then to 5,274 bytes / 16 blocks after launchd ran the rotator. The active log is far below the 100 MiB threshold and is not sparse.

`com.portal5.log-rotate` was installed through `_install_log_rotation_agent` in `scripts/lib/util.sh`, using the repository's sed-placeholder and `launchctl bootstrap` pattern. `plutil -lint` passed for the source and installed plists. `launchctl print gui/501/com.portal5.log-rotate` showed it loaded with a 3,600-second interval and output at `~/.portal5/logs/log-rotate.launchd.log`. A manual `launchctl kickstart` completed; the job was idle afterward with `runs=1`.
