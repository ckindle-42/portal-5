## Watchdog trip: a false positive, corrected

Evidence: [W2_watchdog.log](W2_watchdog.log) (build-time trip) and [W2_live_watchdog.log](W2_live_watchdog.log) (live run).

The build-time trip at 13:20:01 UTC fired on free swap (791 MiB) alone, while memory free was 87% and oMLX was empty. That is not a hazard on macOS: swap is allocated on demand in 1 GiB swapfiles, so `vm.swapusage` free routinely sits under 1 GiB on an idle host holding stale swapped pages. Measured during this review on an idle host: 983 MiB free swap, 84% memory free, `kern.memorystatus_vm_pressure_level=1` (normal), 10 × 1 GiB swapfiles. During the live run, free swap dipped to 421 MiB at 87% free and normal pressure. In the 2026-10-07 incident, by contrast, swap free reached 0 **and** pageable memory was exhausted.

Correction in `scripts/memory_safety_watch.py`: trip on kernel pressure level critical (`kern.memorystatus_vm_pressure_level` = 4, or memory free ≤ 5%), or on free swap below `WATCH_SWAP_FLOOR_MB` **while** memory free is also below `--memory-floor-pct` (default 20). Each sample now logs `pressure_level`. Unit tests cover the incident shape tripping and the W2 false-trip shape not tripping. The earlier missing oMLX bearer header fix is kept. The provisional `unit-known-limitations-host-memory-safety-swap-floor-trip-during-build` unit was withdrawn: the trip was a watchdog defect, not a host limitation.

The interrupted unit gate was re-run: the only failure was a stale `766 canonical units` claim in `unit-capability-wiki` (now 765 after the withdrawal), which was corrected.

## Second trip (live run, 14:09:10 UTC): genuine, transient, recovery defects fixed

With the corrected watchdog running, memory free fell 43% → 18% in four seconds (14:09:06–10) and the kernel pressure level reached 2 (warning). Swap free was 942 MiB, so it tripped on the combined low-swap + low-memory condition, as intended. At that moment: the unit gate was running; oMLX held the two seats warmed by the pipeline restart (`VulnLLM-R-7B-4bit`, `Huihui-Qwen3.5-9B`, about 9.7 GB, and its enforcer evicted VulnLLM at soft pressure); and Ollama ran no load (log shows only a `/api/show`). The macOS log shows only idle-exit reclaim (`JETSAM_REASON_MEMORY_IDLE_EXIT`) and swapfile growth (10 → 20 GiB). There were no jetsam kills of active processes. Memory free recovered to 66%.

The consumer was **not attributed**. No per-process sample existed at the trip. A clean re-run of the full unit suite under a 1 s sampler stayed at 63–75% free throughout (2988 passed), so the suite does not reproduce it. The watchdog now logs the top resident processes at every trip, so the next one can be attributed.

The trip exposed two recovery defects, both fixed and unit-tested:
- Ollama unload used `.env`'s `OLLAMA_URL=http://host.docker.internal:11434`, which does not resolve on the host (`URLError: nodename nor servname`). It is now rewritten to `localhost`, as `native-mcp-service.sh` does.
- oMLX unload aborted the whole loop on the first error. The error was a 400 "Model not loaded" because oMLX's own enforcer had evicted that model a second earlier. Each model is now tried independently.

Side finding (pre-existing, not memory-related): some unit tests reach a live `localhost:9099/ollama/{show,ps}` (pipeline logged 401s during the run; before W2 they hit `:11434` directly). They pass either way because an unreadable ceiling disables the check. Recorded in the closeout.
