# Config files — the config/ tree index

The `config/` tree holds 9 config files; each line below says what the
file is, who writes it, and who reads it. Hand-edited files are operator
inputs; derived files are regenerated by `./launch.sh sync-config` and must
never be edited by hand.

## Hand-edited (operator-owned)

- `portal.yaml` — single source of truth for `workspaces` and `mcp_fleet`;
  written by the operator, read by `sync-config` and the routing layer.
- `backends.yaml` — the model catalog plus memory budgets and `workspace_routing`;
  the one file an operator edits to scale from 1 to 12 nodes.
- `lab_targets.yaml` — lab host/vm targets for bench and live-exec lanes.
- `security_corpus.yaml` — security corpus definitions.
- `tool_catalog.yaml` — tool catalog declarations.
- `challenge_classes.yaml` — challenge classification vocabulary.

## Derived (regenerated, never hand-edited)

- `modules.generated.yaml` — module enabled/disabled state, derived by
  `sync-config` from the module-unit fences and `portal.yaml`.
- `spine_surfaces.yaml` — the code-surface coverage manifest (BR gate),
  generated by `python3 -m portal.platform.wiki.coverage --write-manifest`.
- `complexity_budget.yaml` — recorded complexity ceilings, written by
  `scripts/complexity_report.py --write-budget`; re-baselined after
  intentional code growth.

## Why

The split is the whole config discipline: operator-owned files carry intent,
derived files carry fact, and the `sync-config` / `--write-manifest` /
`--write-budget` trio is what keeps the derived set equal to a fresh
generation. Knowing which bucket a file is in tells an operator what to edit
and what to never touch.
