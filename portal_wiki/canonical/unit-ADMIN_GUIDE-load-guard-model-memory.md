#### Load guard: model memory admission and tuning

The load guard (`portal/platform/inference/load_guard.py`) is the Pipeline's host-memory admission control for model loads on both engines. Ollama and oMLX draw from one unified-memory pool but each engine admits a load from its own view; the 2026-10-07 watchdog reset (`docs/reports/INCIDENT_20261007_WATCHDOG_RESET.md`) is what happens without a shared gate. Every Pipeline request to either engine reports through it, so it counts in-flight requests per (engine, model) and serialises cold loads across worker processes: each worker keeps its own asyncio lock, backed by a host-wide `cold-load.lock` file lock under `/tmp/portal-5-load-guard`, and per-model `flock` activity locks track busy models across workers — `admit_and_begin_ollama` leases that lock through request completion, reserving the model operation across workers so one worker's unload or load never collides with another's. It frees idle models rather than admitting a load that fits only by evicting a model that is serving a sibling request, and it makes room across the engine boundary in both directions: a cold load on either engine frees the other engine's idle residents (least recently used first, stopping once the shortfall is covered) before it refuses, so an Ollama seat is not refused with a 507 while oMLX holds idle memory, and an oMLX seat does not load into memory Ollama could have released. The incoming model's own copy on the other engine — resolved through `config/backends.yaml` aliases — is evicted last, because that is where the same seat may be served next, and a model the router has just failed over from is not evicted until its cool-down expires (`LOAD_GUARD_FAILOVER_PROTECT_S`, 300 s) — and even then only after every other idle source: protection orders eviction and never refuses a request, so an idle shield (failover or keeper) yields when its bytes are the last thing between a request and a refusal, and only in-flight work and the pinned router model are never evicted (2026-11-26: an idle 17.5 GiB failover shield blocked every oMLX seat for its whole window). The ceiling itself is cross-engine: oMLX derives its dynamic ceiling from host free and inactive memory, so an Ollama resident takes all but the engine's `other_app_reclaim_ratio` of its footprint off the room a loaded oMLX seat prefills in (2026-11-20: a 24.6 GiB resident left oMLX 23.22 GB of its 58.88 GB static cap and the engine refused a 2k-token prefill on its loaded 21.16 GB seat). Before admitting an Ollama cold load the guard projects that ceiling from oMLX's live `final_ceiling`, the reclaim share of the engine's memory-guard tier, and the bytes of the loaded seats it may not free (busy, pinned, loading, failover-protected, or the incoming seat's other-engine copy); the load is capped at what leaves them their prefill share, idle residents are evicted first, and it is refused only when nothing frees enough. When the engine's numbers cannot be read the guard fails open and logs that it did. The host-wide cold-load lock is released on every path out of admission — a refusal, a cancellation, any exception, and the request's own end — and otherwise as soon as the model shows resident, so an abandoned or failed request cannot wedge the next cold load. An Ollama cold load that does not fit waits inside the caller's load budget: a free the guard issues stays pending until Ollama's `/api/ps` drops the model and headroom covers its bytes, and the request is refused HTTP 507 only when that budget runs out (the router cascades a 507 as a capacity rejection). When oMLX's status cannot be read the guard fails open and admits, logging loudly. Resident models — the router model, task routers, warm seats — never wait.

#### Knobs

`.env` values, passed into the Pipeline container by `deploy/portal-5/docker-compose.yml`; restart the pipeline container to apply.

- `LOAD_GUARD` (default 1): 0 disables admission entirely; in-flight tracking stays on. Change it only to confirm a refusal is the guard's.
- `LOAD_GUARD_FACTOR` (default 1.25): multiplier on the weights on disk when the guard cannot size the model's KV cache from its own geometry; it stands in for that KV, so a footprint that adds a sized cache does not apply it. A footprint observed the last time the model was resident overrides either estimate. Raise it only if large cold loads with unsizable geometry repeatedly stall near the limit; lower it only against measured footprints.
- `LOAD_GUARD_MARGIN_GB` (default 2): memory kept free after an admitted load, for everything on the host that is not a model. Raise it when non-model processes grow (bigger caches, parallel test workers).
- `OMLX_PREFILL_SAFE_ZONE_RATIO` (default: the engine's own `memory.prefill_safe_zone_ratio`, read by `./launch.sh up`; it is not settable through oMLX's settings API in 0.7.3): share of oMLX's headroom a cold load may occupy. oMLX aborts a request mid-prefill once process usage passes its hard watermark (0.95 of the dynamic ceiling) and prefill needs room above a model's static estimate — on 2026-11-16 an admitted 16.6 GiB seat reached 19.8 GiB of a 20.7 GiB ceiling and died after the stream had started. With the share reserved, the guard frees idle models of either engine to make the room instead of admitting that abort, so a tight oMLX seat costs a reload rather than a failed answer. Empty or unreadable = budget the raw headroom (the pre-2026-11-16 behaviour). The same share governs a *resident* seat: once its usage has eaten the share, the guard frees idle residents of either engine before dispatching the request, and an oMLX abort that still reaches a started stream frees them once and re-issues that request before the error goes to the user (2026-11-19).
- `OMLX_MEMORY_GUARD_TIER` (default: the engine's own `memory.memory_guard_tier`, read by `./launch.sh up`): the tier decides the share of other apps' active memory oMLX reclaims into its ceiling (`safe` 0, `balanced` 0.25, `aggressive` 0.5; a `custom` ceiling is fixed), so it decides how much of an Ollama resident comes off the room a loaded oMLX seat prefills in. Empty or unreadable = no cross-engine projection, the pre-2026-11-20 behaviour.
- `LOAD_GUARD_CEILING_GB` (default 0): 0 budgets against oMLX's live `final_ceiling`, which the balanced tier derives from host free memory, so the same load's verdict can change through the night (P5-OMLX-CEILING-001). Set a fixed GiB budget to make the verdict a property of the model set rather than of the moment; the cap governs Ollama admission only — oMLX's own guard never sees it. `POST /admin/seat-fit` reflects this split: `over_budget` is the live snapshot (a seat above the budget left when every evictable resident is reclaimed), while `never_fit` is asserted only against a fixed budget — with a live ceiling "never" is a claim about the moment, not the seat, so it is not asserted.
- `LOAD_GUARD_WAIT_S` (default 120): how long an interactive cold load waits for memory before HTTP 507. Batch callers override it per request with the header `X-Portal-Load-Wait: <seconds>` (capped at one hour); compliance's pipeline calls send their own larger budget via `COMPLIANCE_LOAD_WAIT_S`.
- `defaults.hot_seat_protect_s` in `config/backends.yaml` (shipped default 0 = off; production runs 900 — a 15-minute window — since 2026-10-22): seconds after an oMLX model's last request during which a *different* oMLX model's request is steered to another candidate instead of deep-resetting the seat's warm prefix cache (P5-OMLX-PREFIX-CACHE-001). Turn it on when two seats share the oMLX engine and one keeps re-paying a cold prefix; it never denies service, never reorders a pinned `::model=` request, and each Pipeline worker tracks its own seats.
- `defaults.preferred_residents` in `config/backends.yaml` (shipped empty; emptied by `ad7163296` on 2026-11-20): workspace ids whose model is loaded at `up` — or at the first idle moment, when the host has no room then — and kept with `keep_alive: -1`; a preferred resident is protected (evicted after every unprotected idle resident), never pinned, so the load guard frees it before it would refuse another seat. It held `auto-daily` while a cold 23.7 GiB daily driver measured a 40 s first token (2026-11-16), but that resident shrank oMLX's dynamic ceiling until its seats were refused at prefill and thrashed between engines; `auto-daily` now loads on demand and pays a cold first token.

#### Watching it work

Admissions, wait seconds, free settles, unloads, and refusals are Prometheus counters and histograms (`portal5_load_guard_admissions_total`, `portal5_load_guard_wait_seconds`, `portal5_load_guard_free_settle_seconds`, `portal5_load_guard_unloads_total`, `portal5_load_guard_refusals_total`), and the headroom and ceiling at the last decision are gauges (`portal5_load_guard_headroom_bytes`, `portal5_load_guard_ceiling_bytes`). The Grafana dashboard `config/grafana/dashboards/portal5_model_management.json` ("Portal 5 — Model Management (Load Guard)") charts them, and the Overview dashboard carries a load-guard row. `portal5_load_guard_wait_seconds` records each wait episode labelled `waited_on` (`in_flight`, `free_settle`, `engine_transition`, `model_operation`); `portal5_load_guard_free_settle_seconds{engine}` times how long a guard-issued free took to show as released (Ollama `/api/ps` drop, oMLX queued-unload counter drop). Refusals bucket by the reason their raise site records: `projected-exceeds` (the load will not fit), `free-settle` (a free the guard issued did not settle within the load wait), `transition-active` (oMLX mid-swap for the whole wait), `quiet` (nothing in flight could free the memory — waiting cannot help until something else changes), `deadline` (another cold load or model operation held the lock past the wait), and `coordination-unavailable` (the cross-process lock directory cannot be used). A turn no candidate could serve is counted separately in `portal5_no_answer_total`. Batch work can ask `POST /admin/load-plan` whether a set of models fits together right now, and run in fit-sized waves instead of discovering the answer as refusals.

#### Why

Two engines, one memory pool, and no engine that can see the other's view is exactly the shape that produced the watchdog reset: each engine admits from its own number, and both are right at the moment they ask. The guard makes admission a property of the host by serialising the loads and charging them against one measured budget, and it makes refusals rare by freeing idle memory and waiting inside the request's own budget first. That is why the knobs are memory figures and wait budgets rather than concurrency limits: the failure being prevented is running the machine out of swap, not overloading a server. The fixed ceiling exists because a verdict that moves with free memory cannot be reasoned about at all — an operator who wants the same answer for the same load all night buys that by fixing the budget, at the cost of also fixing what everything else on the host may use.
