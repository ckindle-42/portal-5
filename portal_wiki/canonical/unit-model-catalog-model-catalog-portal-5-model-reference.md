`MODEL_CATALOG.md` is a rendered model catalog, not a runtime input. The authoritative
model inventory behind it is `config/backends.yaml`, and the fact-unit seeder
`portal/platform/wiki/adapters/seed_facts.py` derives the catalog mechanically:
`derive_model_catalog` loads the registry, `_group_models` unions every model id under
each backend entry's `group` name (a union across entries, so backends sharing one
group both contribute rather than the later entry clobbering the earlier), and emits
the `unit-fact-model-catalog` unit listing the total id count plus one section per
group. Keeping the catalog current means editing the registry and re-running the
seeder; there is no separate hand-maintained list to keep in sync.

## Why

The prior body claimed the catalog was generated by an M2 refactor and maintained
manually thereafter; the seeder proves the derivation is mechanical and current, so
that provenance was wrong and is fixed here. derive_model_catalog reads
config/backends.yaml directly and groups ids per backend group, which is exactly what
an operator needs to know when editing the registry. The institutional caveat that
this file is not parsed at runtime survives as operator guidance.
